# ESP-NOWの設計・運用ガイド

この文書は`espnow/core` を保守するときの設計上の制約と、アプリを作るときの判断基準をまとめたものです。実装済みのガードレールと利用側への推奨事項を分けて記載します。API、既定値、通信形式の詳細は [README](./README.md) を参照してください。

ESP-NOWの送信順序、無線チャネル、到達確認に関する制約はCでもJavaScriptでも共通です。一方、ESP-IDFのコールバックはWi-Fiタスクで動き、このモジュールの公開コールバックは通知を経由してXS側で動きます。この実行場所の違いを前提に設計します。

## core側の観点

### 実装済みのガードレール

ここでいうcoreは `core.ts` と `core.c` です。通常の `espnow` ラッパーや追加レイヤーの `espnow/reliable` の機能は含みません。

| 項目                   | coreの動作                                                                           | 保証の範囲・利用側で対応すること                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 送信の直列化           | 同時に受け付ける送信は1件。完了通知まで次のwriteを拒否                               | onSentを受けて次を送る。待機キューや通知待ちのタイムアウトはcoreにない                                          |
| コールバックの実行場所 | C側で必要な受信データ・メタデータをコピーし、XS側へ通知                              | JS側の重い同期処理によるイベント処理の遅延は防がない                                                            |
| 受信負荷               | C側の通知待ちとJS側の未読パケットを合わせてreceiveQueueLength件まで受け入れる        | 上限を超える新着パケットはコピー・通知の確保・ArrayBufferの生成前に破棄。read後にアプリが蓄積するデータは対象外 |
| 負荷の観測             | infoで受信待機数、受信破棄数、送信通知破棄数を公開                                   | 無線上の全損失を数えるものではない。カウンターは再初期化でリセット                                              |
| 引数の検証             | Byte Buffer、MACの形式、鍵の16バイト長、チャネル値、自機の送信長上限を検証           | payloadの意味、送信者の権限、相手の受信上限は検証しない                                                         |
| チャネル変更           | AP接続中のconfigureによる変更を拒否                                                  | 相手とのチャネルの一致、APの切り替え・スキャン・省電力との調整はアプリが管理                                    |
| 暗号鍵                 | PMK・LMKの設定を提供し、ブロードキャストへのLMK指定を拒否。getPeerからLMKを返さない  | 鍵の生成・配布・保管・更新や、PMK未指定時の既定値の扱いはアプリが決める                                         |
| 終了と寿命             | closeを複数回呼べる。close後の公開通知を止め、通知待ちのネイティブデータの寿命を管理 | Wi-Fiはcoreが所有しない。アプリがcoreを閉じてからWi-Fiを閉じる                                                  |

writeの正常終了はESP-IDFが送信を受け付けたことを示し、onSentのsuccessはMAC送信結果を示します。相手アプリの受信・検証・処理完了を意味しません。ブロードキャストのMAC成功からはどの相手が受信したかも判断できません。

### coreを変更するときに守ること

1. Wi-Fiタスクの処理は短く済ませて返します。ネイティブコールバックから直接JSを実行せず、JSON解析、アプリ処理、待機、再送ループ、パケットごとの大量ログを追加しません。共有状態の排他区間も短く保ちます。
2. ESP-IDFの一時ポインターを保存しません。受信データ、送信元・宛先、RSSIなど、後で使う値はコールバックが返る前に所有する領域へコピーします。XSから取得したバッファポインターもGCを起こし得るAPI呼び出しをまたいで保持しません。
3. 受信枠は通知する前に確保します。JS側の配列だけに上限を設けても、通知に使うメモリは制限できません。通知に失敗した場合は枠と参照を戻し、破棄数を増やします。通知をJSへ渡しただけでは枠を戻さず、readでパケットを取り出すまで管理します。
4. 完了通知と送信中の1件との対応を保ちます。遅延した通知を次の送信の結果にしてしまうため、通知がないまま送信中フラグだけを解除して次のwriteを許可することはしません。通知に失敗しても成功として補完しません。
5. close・例外・再初期化の前後でデータの寿命と通知先を管理します。ユーザーコールバックがcloseしたり例外を投げたりしても、参照を二重解放せず、古いインスタンス向けの通知を新しいインスタンスに渡さない設計を維持します。
6. アプリの通信形式をcoreに組み込みません。ACK、連番、発見、再送、JSON、分割・再構成は別レイヤーで扱います。公開APIの形式や有効期間、通知の意味を変える場合は、型・README・テストも更新します。

coreを変更したときは正常系に加え、受信上限、通知の確保失敗、送信通知の紛失、closeと通知の前後関係、遅延通知を確認します。ホスト上のテストに加えて対象ESP32向けにビルドし、無線やタスク間の動作を変えた場合は実機でも確認します。

## アプリ側の観点

### 用途に合う送信方法を選ぶ

| 用途                                        | 選択の目安                                 | アプリで決めること                                                                            |
| ------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 順番に送る通常データ                        | espnow.send                                | キュー超過時の待機・破棄、失敗後に送るかどうか                                                |
| 姿勢・センサー値など最新値が重要なデータ    | espnow.sendLatest                          | 宛先とストリームごとのkey、更新頻度、受信値の有効期限。待機中の置き換えによるrejectも処理する |
| 相手の処理完了を確認したい命令              | espnow/reliable、またはアプリ固有のACK方式 | ACKの意味、期限、最大再送数、重複実行防止、再起動時の履歴                                     |
| コピー・待機キュー・Wi-Fiの管理を自分で行う | espnow/core                                | 上記に加え、送信の直列化、完了通知待ちの監視、終了・再作成                                    |

最新値を送る場合でも、古いデータが送信中なら取り消せません。必要ならpayloadに連番や時刻を持たせ、受信側で古い値を適用しないようにします。送信元が複数の場合や再起動時には、連番の比較単位も定義してください。

### 起動・チャネル・相手の管理

- Wi-Fiを開始して対象インターフェースを有効にしてからcoreを作ります。通常のラッパーがWi-Fiを所有するか、manageWiFi:falseでアプリが所有するかを決め、終了処理も同じ所有者が担当します。
- 単独通信では双方のチャネルをそろえます。AP併用時は接続先APのチャネルを基準にし、再接続やAP変更後もinfo.channelを確認します。channel:0は自機の現在チャネルを使う指定で、相手の探索や全チャネル受信ではありません。
- 送信前に相手を登録します。暗号化ユニキャストやACK返信では両側で登録します。ブロードキャスト相手は自動登録されますが、その1件も登録数に含まれます。SDK・sdkconfigの登録数と暗号化相手数の上限を確認します。
- 送信中・送信待ちの相手を削除したり、鍵やインターフェースを変更したりする操作は避けます。更新時は新しい送信を止め、未完了の送信をどう扱うか決めてから変更します。coreのconfigureは送信中、ラッパーのconfigureは待機中も拒否しますが、相手の登録変更を同じ条件で拒否するわけではありません。
- スキャン、AP接続、他の無線機能、省電力を併用する場合は、その構成で欠落率と遅延を実測します。スリープする受信側には送信時刻と受信可能時間の調整が必要です。このモジュールは受信ウィンドウや省電力の設定を提供しません。

### データ形式・サイズ・受信処理

- info.maxDataLengthは**自機の上限**です。相手の対応が不明、またはv1端末を含む場合は、アプリのヘッダーも含めて250バイト以内にします。espnow/reliableのpayload上限は234バイトです。
- アプリのバージョン、種別、長さ、数値の範囲とバイト順を定義します。Cの構造体のメモリ配置をそのまま通信仕様にせず、DataViewなどで明示します。文字列は文字数でなく、符号化後のバイト数で確認します。
- 受信データは最低限の長さを確認してからデコードし、種別・バージョン・値の範囲が正しいことを確かめてからアプリの状態を変えます。coreはpayloadの形式を保証しません。
- 公開コールバックはXS側で動きますが、長い同期ループや大量ログは受信通知・送信結果・タイマーを遅らせます。重い処理は小さく分割し、後段の待機キューにも上限と破棄方針を設けます。
- onReceiveやonReadableをasync関数にしても、モジュールは返されたPromiseを待ちません。開始する非同期処理の数と失敗をアプリ側で管理します。espnow/reliableのonCommandは返されたPromiseを待ちます。処理完了をACK条件にするなら、その処理のPromiseを返します。

### 到達確認・再送・復旧

- MAC送信失敗、MAC送信成功、アプリACK成功を分けて記録します。ACK待ちのタイムアウトは「相手が処理していない」という証明にはなりません。処理後のACKだけが失われる場合もあります。
- 命令の再送では同一の実行IDを使って重複を判定します。「値を設定する」のような冪等な命令にするか、必要な実行履歴を永続化します。副作用を起こしてからthrow/rejectした場合も、再試行で副作用が重複し得ます。
- 再送回数と待ち時間に上限を設け、失敗後の停止・通知・再接続を決めます。自作の再送方式で多数の端末が同時に再送する場合は、待ち時間を延ばしたりランダムにずらしたりすることを検討します。espnow/reliableの再送間隔は固定で、この調整を自動では行いません。
- MAC完了待ちのsendTimeoutとMAC成功後のackTimeoutを別々に決めます。通常時だけでなく、処理負荷・スリープを含む遅延を測って設定します。JSが停止している間はタイマーのコールバックも実行できないため、厳密な実時間の期限には使いません。
- 通常のラッパーがfaultedになったら、recoverの成功を確認してから新規送信を再開します。復旧に失敗した場合の待機時間と試行回数を決め、無限の即時再試行を避けます。coreを直接使う場合は、完了待ちのタイムアウト時にcloseして作り直し、相手と鍵を再登録します。
- reliableのsessionIdは起動・再作成ごとに更新し、同じ送信元で同一sessionの送信レイヤーを並行して動作させません。receiveSessionLimitまで履歴を使った場合、新しいsessionは受け付けません。履歴の消去・レイヤーの再作成は、遅延パケットが残らない運用と組み合わせます。再起動をまたぐ保証はアプリで用意します。

### 暗号化・受信元の扱い

- 暗号化するユニキャストでは独自のPMKと相手ごとのLMKを設定し、相手側にも同じLMKを登録します。PMKを設定するだけではpayloadは暗号化されません。サンプルの鍵や既定PMKを本番の鍵として使わず、実際の鍵をログに出さない運用にします。
- MAC、RSSI、broadcastの値を認証の代わりにしません。許可する相手・命令をアプリで定義し、保護が必要な命令は暗号化ユニキャストなど、認証できる経路で扱います。発見用のブロードキャストと命令の受け付けを分け、受信のたびに無条件で相手を登録しないようにします。
- ブロードキャストはESP-NOWの暗号化対象にできず、全員の受信確認もありません。受信者全員から一斉にACKを返す設計を避けます。espnow/reliableはユニキャスト専用であり、ACK・連番自体が新たな認証機能を提供するわけではありません。

## 実機で確認すること

| 条件                                     | 観測する結果                                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 通常負荷と想定する最大負荷               | MAC成功率、アプリACK成功率、返信遅延、pending、receivePending、receiveDropped、送信通知破棄数      |
| 受信処理が送信頻度に追いつかない         | 破棄数が増えても待機件数とメモリが増え続けない。最新値の遅延や命令の失敗をアプリが検出できる       |
| 相手の電源断・チャネル不一致・鍵の不一致 | 成功として処理せず、期限と試行回数の範囲で失敗する                                                 |
| ACKだけの紛失・重複・遅延                | 同じ命令を二重に実行しない。別の命令のACKとして扱わない                                            |
| 送信完了通知の紛失と復旧                 | 未完了の送信が失敗になり、復旧後に遅延通知で新しい送信を誤って完了させない。必要な設定が復元される |
| close・再作成・端末再起動                | close後に通知しない。タイマーやメモリが残り続けない。sessionと実行履歴が設計どおりになる           |
| AP併用・スキャン・省電力                 | 実際のチャネルと受信可能時間で、想定する欠落率・遅延に収まる                                       |

カウンターは起動時と負荷後の差分で比較し、再初期化によるリセットも記録します。RSSIだけで通信の健全性を判断せず、返信と欠落を実測するときの補助情報とします。ホスト上のテストやシミュレーターでの成功は、実機の無線・メモリ・タイミングの検証とは分けて扱います。

## 根拠と実装の確認先

ESP-NOW固有の仕様は使用するESP-IDF・チップの公式資料で確認してください。このガイドでは [ESP-IDF v6.1 / ESP32 ESP-NOW](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/api-reference/network/esp_now.html) の送信・受信、チャネル、暗号化、初期化順序を参照しています。対応する最大長や登録上限がすべてのSDK・端末で同じ値だと仮定しないでください。

このモジュールのガードレールは [core.ts](./core.ts) と [core.c](./core.c) に実装されています。通常のラッパーのキューと復旧は [espnow.ts](./espnow.ts)、命令のACK・再送・重複排除は [reliable.ts](./reliable.ts) にあります。SDK側では `guides/callbacks`、`guides/binary`、`guides/wifi` と `documentation/xs/XS in C.md` のメモリ安全性を参照します。SDKのGuideにESP-NOW専用の項目はないため、一般のECMA-419 I/Oの慣例と、この独自APIの保証は区別してください。
